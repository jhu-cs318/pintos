#### ALGORITHMS

>A2: Briefly describe how you implemented argument parsing.  How do you arrange for the elements of argv[] to be in the right order?
>How do you avoid overflowing the stack page?

1. **Parsing:**
   In `process_execute()`, a copy of the command-line string is made onto a kernel page (`fn_copy`) allocated with `palloc_get_page(0)`. The executable name is parsed to assign the thread name. In `start_process()`, the command line is passed to `load()`, where `strtok_r()` parses the string by spaces into an array of argument pointers `argv[]`, keeping track of `argc`.

2. **Arranging `argv[]` in the right order:**
   Arguments are pushed following the 80x86 calling convention:
   - First, argument strings are copied onto the stack in reverse order (`argv[argc - 1]` down to `argv[0]`), and their new virtual stack addresses are saved in `arg_addrs[]`.
   - The stack pointer is rounded down to a 4-byte boundary for word alignment (`*esp -= (uintptr_t)*esp % 4`).
   - A null pointer sentinel (`argv[argc] = NULL`) is pushed.
   - Pointers to the strings are pushed in reverse order (`arg_addrs[argc - 1]` down to `arg_addrs[0]`). Because `arg_addrs[0]` is pushed last, it sits at the lowest address, which becomes `argv[0]`.
   - The address of `argv[0]` (the `argv` pointer itself), followed by `argc`, and finally a dummy return address `NULL` are pushed onto the stack.

3. **Avoiding stack overflow:**
   Before each stack decrement and write, we verify that `(uint8_t *)*esp >= (uint8_t *)PHYS_BASE - PGSIZE`. If pushing arguments would exceed the allocated 4 kB stack page, argument setup aborts and `load()` returns `false`, gracefully terminating the process.

#### RATIONALE

>A3: Why does Pintos implement strtok_r() but not strtok()?

`strtok()` uses an internal static variable to preserve state across successive calls. This makes it non-reentrant and unsafe in a multi-threaded OS kernel: if one thread is preempted during tokenization and another calls `strtok()`, the static state is overwritten. `strtok_r()` requires the caller to provide a `save_ptr` variable, storing state in caller-owned stack memory, ensuring thread safety and reentrancy.

>A4: In Pintos, the kernel separates commands into a executable name and arguments.  In Unix-like systems, the shell does this separation.  Identify at least two advantages of the Unix approach.

1. **Security and Kernel Simplicity:** Performing parsing in user space keeps complex string manipulation and potential buffer overflow vulnerabilities out of the privileged kernel space, reducing the kernel attack surface.
2. **Flexibility and Shell Features:** User-space shells can implement rich functionality like wildcards/globbing (`*`), environment variable expansion (`$VAR`), pipes (`|`), and I/O redirection (`<`, `>`) without complicating or bloating the kernel.

>B2: Describe how file descriptors are associated with open files. Are file descriptors unique within the entire OS or just within a single process?

File descriptors are associated with open files via `struct file_descriptor` nodes maintained in a per-process list (`thread_current()->fds`). 

File descriptors are unique **just within a single process**. Each process maintains its own descriptor list and an independent `next_fd` counter starting at 2 (with 0 reserved for STDIN and 1 for STDOUT). Different processes can hold the same descriptor integer referencing completely different open files.

#### ALGORITHMS

>B3: Describe your code for reading and writing user data from the kernel.

All user-supplied pointers, buffers, and strings are validated before being dereferenced:
- `is_valid_user_ptr()` verifies that a pointer is non-null, below `PHYS_BASE`, and mapped in the active page directory via `pagedir_get_page()`.
- `is_valid_user_buffer()` verifies that `buffer + size - 1` does not wrap around, stays below `PHYS_BASE`, and every page spanned in the range is mapped.
- `is_valid_user_string()` scans each page up to the null-terminator, ensuring each page crossed is mapped.
- For reading user data (e.g. system call arguments from user stack), `get_syscall_args()` validates the stack memory with `is_valid_user_buffer()` before reading.
- In `sys_read()`, destination buffer validity is checked. For fd 0, input is read via `input_getc()`. For fd >= 2, `filesys_lock` is acquired and `file_read()` copies disk data into the verified user buffer.
- In `sys_write()`, source buffer validity is checked. For fd 1, console output is written via `putbuf()`. For fd >= 2, `filesys_lock` is acquired and `file_write()` writes user buffer data to disk.

>B4: Suppose a system call causes a full page (4,096 bytes) of data
>to be copied from user space into the kernel.  What is the least
>and the greatest possible number of inspections of the page table
>(e.g. calls to pagedir_get_page()) that might result?  What about
>for a system call that only copies 2 bytes of data?  Is there room
>for improvement in these numbers, and how much?

- **4,096 bytes:**
  - Least: 1 inspection, if the buffer is page-aligned (occupies exactly one page).
  - Greatest: 2 inspections, if the buffer is not page-aligned and straddles two distinct physical pages.
- **2 bytes:**
  - Least: 1 inspection, if both bytes reside on the same page.
  - Greatest: 2 inspections, if the 2 bytes span across a page boundary (byte 0 at offset 4095 of page N, byte 1 at offset 0 of page N+1).
- **Room for improvement:**
  - Our page-stepping algorithm performs only 1 or 2 lookups, which is optimal for software validation.
  - Improvement can be achieved by eliminating software page table lookups altogether, relying instead on MMU page fault handling with inline assembly instructions (`get_user` and `put_user`). This reduces software lookups from 1-2 down to 0 during normal operation.

>B5: Briefly describe your implementation of the "wait" system call
>and how it interacts with process termination.

- `sys_wait(pid)` invokes `process_wait(pid)`.
- `process_wait()` searches the calling thread's `children` list for a child whose `tid` matches `pid`.
- If not found or if `child->waited` is true, -1 is returned immediately.
- It sets `child->waited = true` and executes `sema_down(&child->exit_sema)`.
- If the child is still running, the parent blocks. When the child terminates in `process_exit()`, it writes its exit code into `child->exit_status` and calls `sema_up(&child->exit_sema)`.
- If the child already terminated before `wait` was called, `exit_sema` is already 1, so `sema_down` returns without blocking.
- The parent retrieves `child->exit_status`, removes the child from `children`, and calls `child_release()` to free the child record.

>B6: Any access to user program memory at a user-specified address
>can fail due to a bad pointer value.  Such accesses must cause the
>process to be terminated.  System calls are fraught with such
>accesses, e.g. a "write" system call requires reading the system
>call number from the user stack, then each of the call's three
>arguments, then an arbitrary amount of user memory, and any of
>these can fail at any point.  This poses a design and
>error-handling problem: how do you best avoid obscuring the primary
>function of code in a morass of error-handling?  Furthermore, when
>an error is detected, how do you ensure that all temporarily
>allocated resources (locks, buffers, etc.) are freed?  In a few
>paragraphs, describe the strategy or strategies you adopted for
>managing these issues.  Give an example.

We solved this through pre-validation at boundaries combined with centralized resource reclamation:

1. **Pre-validation at system call entry:**
   Instead of scattering error checks throughout system call implementations, pointers, buffers, and string parameters are validated *before* any locks are acquired or heap resources allocated. If any check fails, `syscall_exit_fail()` is called, setting `cur->exit_status = -1` and calling `thread_exit()`.

2. **Centralized cleanup in `process_exit()`:**
   Regardless of whether termination is triggered by normal exit, memory validation failure, or a CPU page-fault exception, `thread_exit()` unconditionally invokes `process_exit()`. `process_exit()` performs complete resource reclamation: closing all open file descriptors, closing the executable file (re-enabling writes), releasing `filesys_lock` if held by the current thread, and freeing allocated child records and page tables.

3. **Example:**
   In `sys_write(fd, buffer, size)`, `is_valid_user_buffer(buffer, size)` validates the full buffer range before calling `filesys_open()` or `lock_acquire(&filesys_lock)`. If `buffer` is invalid (e.g., NULL or in kernel space), `syscall_exit_fail()` is triggered immediately. Because the lock was not yet acquired, no locking state is corrupted. Furthermore, even if an unexpected exception occurs, `process_exit()` checks `lock_held_by_current_thread(&filesys_lock)` and releases it automatically.

#### SYNCHRONIZATION

>B7: The "exec" system call returns -1 if loading the new executable
>fails, so it cannot return before the new executable has completed
>loading.  How does your code ensure this?  How is the load
>success/failure status passed back to the thread that calls "exec"?

- In `process_execute()`, the parent creates a `struct process_child` with semaphore `load_sema` initialized to 0 and `load_success` initialized to `false`.
- After calling `thread_create()`, the parent calls `sema_down(&child->load_sema)` and blocks.
- The new child thread starts executing in `start_process()`, attempts to load the executable with `load()`, stores the boolean result in `child->load_success`, and calls `sema_up(&child->load_sema)`.
- The parent wakes up from `sema_down()`. If `!child->load_success`, the parent removes the child record from its list, releases its reference, and returns `TID_ERROR` (-1). If loading succeeded, the parent returns the child's `tid`.

>B8: Consider parent process P with child process C.  How do you
>ensure proper synchronization and avoid race conditions when P
>calls wait(C) before C exits?  After C exits?  How do you ensure
>that all resources are freed in each case?  How about when P
>terminates without waiting, before C exits?  After C exits?  Are
>there any special cases?

We manage `struct process_child` with an atomic reference count (`refs = 2` initially) protected by interrupt disabling:

1. **P calls `wait(C)` before C exits:**
   P calls `sema_down(&child->exit_sema)` and blocks. When C terminates in `process_exit()`, C records its `exit_status`, calls `sema_up(&child->exit_sema)`, and decrements `refs` (2 -> 1). P wakes up, reads `exit_status`, removes C from its list, and decrements `refs` (1 -> 0), freeing the struct.
2. **P calls `wait(C)` after C exits:**
   C has already recorded `exit_status`, called `sema_up(&child->exit_sema)`, and decremented `refs` (2 -> 1). When P calls `wait(C)`, `sema_down` returns immediately. P reads `exit_status`, removes C, and decrements `refs` (1 -> 0), freeing the struct.
3. **P terminates without waiting before C exits:**
   In P's `process_exit()`, P pops all children from its `children` list and calls `child_release()`, decrementing `refs` (2 -> 1). When C terminates later, C calls `child_release()`, decrementing `refs` (1 -> 0), freeing the struct.
4. **P terminates without waiting after C exits:**
   C already decremented `refs` upon termination (2 -> 1). When P terminates, P's `process_exit()` iterates over `children` and decrements `refs` (1 -> 0), freeing the struct.
5. **Special Cases:**
   - **Waiting twice on C:** On the first wait call, C is removed from P's `children` list. Any subsequent `wait(C)` fails to find C and immediately returns -1.
   - **Waiting on non-child:** The PID is not in P's `children` list, returning -1 immediately.

#### RATIONALE

>B9: Why did you choose to implement access to user memory from the
>kernel in the way that you did?

We chose verification prior to dereferencing (Method 1) because it is straightforward, robust, and clean to reason about. In Pintos Project 2, virtual memory is non-paged and static after loading, so checking `is_user_vaddr()` and querying `pagedir_get_page()` reliably verifies memory presence. It isolates invalid accesses before kernel locks are held, eliminating the risk of kernel deadlocks or complex exception recovery paths.

>B10: What advantages or disadvantages can you see to your design
>for file descriptors?

- **Advantages:**
  - Using a dynamic linked list (`struct file_descriptor`) means there is no hard-coded upper limit on open files per process.
  - Memory is allocated on demand and immediately reclaimed on `close()` or `process_exit()`.
  - Descriptors are strictly per-process and isolated.
- **Disadvantages:**
  - File descriptor lookup requires O(N) list traversal instead of O(1) array index access. However, because typical processes only keep a few files open simultaneously, the overhead is negligible.

>B11: The default tid_t to pid_t mapping is the identity mapping.
>If you changed it, what advantages are there to your approach?

We maintained the 1:1 identity mapping between `tid_t` and `pid_t`. Because Pintos does not support multithreaded user processes, each process has exactly one kernel thread. An identity mapping avoids unnecessary mapping tables, translation overhead, and complexity without sacrificing any functionality.
